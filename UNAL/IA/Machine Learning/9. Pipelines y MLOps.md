# 🔧 ML-9 — Pipelines y MLOps

> [!abstract] Idea central
> Un modelo que no se despliega no produce valor. **MLOps** (Machine Learning Operations) es la disciplina que lleva modelos del notebook al sistema productivo de forma confiable, reproducible y sostenible. Un **pipeline** de ML automatiza cada paso: ingesta de datos → preprocesamiento → entrenamiento → evaluación → despliegue → monitoreo. Esta nota cubre el ciclo completo: diseño de pipelines robustos, ingeniería de características, versionado, CI/CD para ML, despliegue como API, y monitoreo de la degradación del modelo en producción.

---

## 1. El problema de la deuda técnica en ML

### 1.1 Por qué los notebooks no son suficientes

El flujo típico de un proyecto de ML en investigación es lineal: exploración → modelo → resultado. En producción, este flujo se convierte en un **sistema continuo** con múltiples fuentes de complejidad:

```
Datos en tiempo real
        ↓
   Preprocesamiento
        ↓
   Feature Engineering  ←── actualización periódica
        ↓
   Entrenamiento/Re-entrenamiento
        ↓
   Evaluación automática
        ↓
   Despliegue (si pasa umbrales)
        ↓
   Serving (API / batch)
        ↓
   Monitoreo ──────────────────→ ¿Drift detectado? → reinicia ciclo
```

> [!warning] La deuda técnica en ML (Sculley et al., NeurIPS 2015)
> Google identificó que el código de ML puro (el modelo) es solo una fracción pequeña de un sistema ML en producción. La mayor parte de la complejidad está en el **código de infraestructura** que lo rodea: ingesta de datos, validación, preprocesamiento, serving, monitoreo. Este código tiende a acumular deuda técnica más rápido que el código de software convencional porque:
> - Los datos cambian continuamente (concept drift, data drift)
> - Los modelos dependen de la distribución de datos en el momento de entrenamiento
> - Los resultados son difíciles de testear unitariamente (¿cómo testear que un modelo es "bueno"?)
> - La reproducibilidad requiere versionar datos, código **y** parámetros simultáneamente

## 2. Ingeniería de características (Feature Engineering)

### 2.1 Transformaciones numéricas

<font color="#00b0f0">Definición 1 — Escalado estándar y robusto</font>

El escalado de características es obligatorio antes de modelos basados en distancias (k-NN, SVM, KMeans) y regularización (Ridge, Lasso, redes neuronales):

$$z_i^{\text{std}} = \frac{x_i - \bar{x}}{\hat{\sigma}_x}, \qquad z_i^{\text{rob}} = \frac{x_i - \text{mediana}(x)}{IQR(x)}$$

El **RobustScaler** es preferido cuando hay outliers (usa la mediana e IQR en lugar de media y desviación estándar). El **MinMaxScaler** mapea a $[0,1]$ preservando ceros — preferido para datos dispersos o cuando la distribución es no gaussiana.

**Transformaciones de varianza estabilizadora:**
- $\log(1 + x)$ para variables con distribución log-normal o sesgada positiva (precios, ingresos, frecuencias)
- $\sqrt{x}$ para conteos (distribución Poisson)
- Box-Cox: $x^{(\lambda)} = (x^\lambda - 1)/\lambda$ si $\lambda \neq 0$, $\log(x)$ si $\lambda = 0$ — estima $\lambda$ óptimo por MLE

### 2.2 Variables categóricas

| Técnica | Cuándo usar | Ventaja | Riesgo |
|---|---|---|---|
| **One-hot encoding** | $K \leq 15$ categorías | Simple, sin ordinalidad implícita | Explosión de dimensiones para K grande |
| **Ordinal encoding** | Categorías con orden natural (bajo/medio/alto) | Preserva orden | Introduce ordinalidad donde puede no haberla |
| **Target encoding** | $K$ grande, clasificación o regresión | Compacto, informativo | Data leakage si no se hace cross-validation |
| **Binary encoding** | $K$ moderado-grande | $\log_2 K$ columnas | Menos interpretable |
| **Hashing trick** | $K$ muy grande (IDs de usuario, URLs) | Memoria fija | Colisiones |
| **Embeddings aprendidos** | $K$ muy grande + DL disponible | Captura similitud semántica | Requiere más datos |

**Target encoding con cross-validation** (evita leakage): para calcular el target encoding de la observación $i$, usar solo las demás observaciones del mismo fold de CV — nunca la propia $i$.

### 2.3 Variables temporales

Las características derivadas del tiempo son frecuentemente las más informativas en series temporales:

- **Ciclicas:** hora del día, día de la semana, mes → transformar con seno/coseno para preservar la naturaleza circular:
$$x_{\text{hora}}^{\sin} = \sin\!\left(\frac{2\pi \cdot \text{hora}}{24}\right), \quad x_{\text{hora}}^{\cos} = \cos\!\left(\frac{2\pi \cdot \text{hora}}{24}\right)$$
- **Rezagos (lags):** $x_{t-1}, x_{t-2}, x_{t-k}$ — incorporan dependencias temporales
- **Ventanas rodantes:** media, desviación, mínimo, máximo en ventana de $w$ pasos
- **Diferencias:** $\Delta x_t = x_t - x_{t-1}$ — convierte series no estacionarias en estacionarias

### 2.4 Imputación de valores faltantes

<font color="#00b0f0">Definición 2 — Mecanismos de datos faltantes (Rubin, 1976)</font>

- **MCAR** (Missing Completely At Random): la probabilidad de que falte un valor no depende de ninguna variable. Imputación simple es válida.
- **MAR** (Missing At Random): la probabilidad de que falte depende de otras variables observadas, no del valor faltante mismo. Imputación múltiple o basada en modelos es válida.
- **MNAR** (Missing Not At Random): la probabilidad de que falte depende del valor faltante mismo (e.g., personas con ingresos muy altos no reportan ingresos). Cualquier imputación introduce sesgo.

**Estrategias de imputación:**
- Media/mediana/moda: simple, introduce sesgo hacia el centro
- KNN-imputer: $k$ vecinos más cercanos por las variables no faltantes; preserva correlaciones
- Iterative imputer (MICE): ajusta un modelo para cada variable con faltantes usando las demás; el más preciso pero más lento
- Indicador binario de faltante: añadir $\mathbf{1}[x_j = \text{NaN}]$ como variable adicional

> [!example] Ejemplo 1 — Pipeline de predicción de demanda en cadena de supermercados
> Datos: ventas diarias de 4.000 SKUs en 50 tiendas durante 3 años. Características: precio, promociones (binaria), día de semana (cíclica), semana del año (cíclica), temperatura exterior, inventario, lags de ventas (t-1, t-7, t-28), medias rodantes (7/14/28 días), indicador de festivo.
> Valores faltantes: ~3% en temperatura exterior (sensor offline) → KNN-imputer con estaciones cercanas. Categorías: SKU (4.000 categorías) → target encoding con CV de 5 folds. El pipeline completo se serializa con `sklearn.Pipeline` para garantizar reproducibilidad y evitar leakage en producción.

## 3. Diseño de pipelines con scikit-learn

### 3.1 El objeto Pipeline

Un `Pipeline` de scikit-learn encadena transformadores y un estimador final, garantizando que:
1. El `fit` del preprocesamiento usa solo los datos de entrenamiento
2. El `transform` de validación/test usa los parámetros aprendidos en entrenamiento
3. El pipeline completo es un objeto serializable (pickleable)

```python
from sklearn.pipeline import Pipeline
from sklearn.compose import ColumnTransformer

preprocessor = ColumnTransformer([
    ("num", Pipeline([
        ("imputer", KNNImputer(n_neighbors=5)),
        ("scaler",  StandardScaler())
    ]), numeric_features),
    ("cat", Pipeline([
        ("imputer", SimpleImputer(strategy="most_frequent")),
        ("encoder", OneHotEncoder(handle_unknown="ignore"))
    ]), categorical_features),
])

pipeline = Pipeline([
    ("preprocessor", preprocessor),
    ("model",        LGBMRegressor(n_estimators=500))
])

pipeline.fit(X_train, y_train)
pipeline.predict(X_test)
```

### 3.2 Transformadores personalizados

Cualquier transformación del negocio puede encapsularse como un transformador sklearn:

```python
from sklearn.base import BaseEstimator, TransformerMixin

class CyclicalEncoder(BaseEstimator, TransformerMixin):
    def __init__(self, max_val):
        self.max_val = max_val
    def fit(self, X, y=None):
        return self
    def transform(self, X):
        return np.c_[np.sin(2*np.pi*X/self.max_val),
                     np.cos(2*np.pi*X/self.max_val)]
```

### 3.3 Feature stores

En sistemas de producción grandes, las características se centralizan en un **Feature Store**: un repositorio que almacena características pre-calculadas con versionado y linaje de datos. Ventajas:
- Reutilización de características entre equipos y modelos
- Consistencia entre entrenamiento y serving (elimina el "training-serving skew")
- Computación offline de características costosas (ventanas rodantes de meses)

Herramientas: Feast, Tecton, Hopsworks, Vertex AI Feature Store.

## 4. Versionado y reproducibilidad

### 4.1 La trinidad de la reproducibilidad

Un experimento de ML es reproducible solo si se versiona simultáneamente:

```
┌─────────────┐   ┌─────────────┐   ┌─────────────────┐
│    CÓDIGO   │   │    DATOS    │   │  HIPERPARÁMETROS │
│   (git)     │ + │  (DVC/S3)  │ + │   (MLflow/W&B)  │
└─────────────┘   └─────────────┘   └─────────────────┘
         ↓               ↓                  ↓
              EXPERIMENTO REPRODUCIBLE
```

### 4.2 Versionado de datos con DVC

**DVC** (Data Version Control) extiende Git para versionar datasets y modelos grandes:

```bash
dvc init
dvc add data/raw/ventas_2024.csv    # rastrea el archivo, almacena en .dvc
git add data/raw/ventas_2024.csv.dvc .gitignore
git commit -m "Añadir dataset ventas 2024"
dvc push                             # sube los datos a S3/GCS/Azure
```

Cuando un colaborador hace `git clone` + `dvc pull`, obtiene exactamente el mismo dataset. Los `.dvc` files son pequeños archivos de texto con el hash SHA-256 del archivo original.

### 4.3 Seguimiento de experimentos con MLflow

**MLflow** organiza experimentos en runs, registrando métricas, parámetros, artefactos y modelos:

```python
import mlflow
import mlflow.sklearn

with mlflow.start_run(run_name="lgbm_v3_target_encoding"):
    mlflow.log_params({"n_estimators": 500, "learning_rate": 0.05,
                       "encoding": "target", "imputation": "knn"})
    pipeline.fit(X_train, y_train)
    rmse = np.sqrt(mean_squared_error(y_val, pipeline.predict(X_val)))
    mlflow.log_metric("val_rmse", rmse)
    mlflow.log_metric("val_mae",  mean_absolute_error(y_val, pipeline.predict(X_val)))
    mlflow.sklearn.log_model(pipeline, "pipeline",
                              registered_model_name="demanda_supermercado")
```

El **MLflow Model Registry** gestiona el ciclo de vida del modelo: Staging → Production → Archived.

## 5. CI/CD para Machine Learning

### 5.1 El problema de testear modelos

En software convencional, los tests son deterministas: dada la misma entrada, la salida es siempre la misma. En ML, los tests deben evaluar propiedades estadísticas:

<font color="#00b0f0">Definición 3 — Niveles de testing en ML</font>

| Nivel | Qué se testea | Herramienta |
|---|---|---|
| **Unit tests de datos** | Esquema, rangos, valores nulos, distribuciones | Great Expectations, Pandera |
| **Unit tests de features** | Que las transformaciones producen el output correcto | pytest + fixtures |
| **Unit tests del modelo** | Que el modelo aprende algo sobre datos triviales | pytest |
| **Integration tests** | Pipeline completo sobre un dataset pequeño | pytest |
| **Slicing tests** | Rendimiento por subgrupo (equidad, robustez) | ML Test Score |
| **Shadow deployment** | Modelo nuevo en paralelo con producción | A/B testing |

**El ML Test Score** (Breck et al., Google 2017) es un checklist de 28 tests que los equipos de Google usan para evaluar la madurez de un sistema ML. Puntuación de 0 (todo manual) a 5 (totalmente automatizado y monitoreado).

### 5.2 Validación automática de datos

**Great Expectations** permite definir "expectativas" sobre los datos que se verifican automáticamente:

```python
import great_expectations as gx

context = gx.get_context()
ds = context.sources.add_pandas("ventas", dataframe=df)
suite = context.add_expectation_suite("ventas_suite")

# Definir expectativas
ds.expect_column_values_to_not_be_null("precio")
ds.expect_column_values_to_be_between("precio", min_value=0.01, max_value=5000)
ds.expect_column_values_to_be_in_set("dia_semana", {0,1,2,3,4,5,6})
ds.expect_column_mean_to_be_between("ventas", min_value=5, max_value=500)

results = context.run_checkpoint("checkpoint_diario")
# Si alguna expectativa falla → pipeline se detiene, alerta enviada
```

### 5.3 Pipeline CI/CD con GitHub Actions

```yaml
# .github/workflows/ml_pipeline.yml
name: ML Pipeline CI/CD

on:
  push:
    paths: ["data/**", "src/**", "configs/**"]

jobs:
  validate-data:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Pull data with DVC
        run: dvc pull
      - name: Run data validation
        run: python src/validate_data.py

  train-and-evaluate:
    needs: validate-data
    runs-on: ubuntu-latest
    steps:
      - name: Train model
        run: python src/train.py --config configs/lgbm_v3.yaml
      - name: Evaluate model
        run: python src/evaluate.py
      - name: Check performance threshold
        run: |
          python -c "
          import json
          metrics = json.load(open('metrics.json'))
          assert metrics['val_rmse'] < 48.0, f'RMSE {metrics[\"val_rmse\"]} > umbral 48.0'
          assert metrics['val_mae']  < 32.0, f'MAE {metrics[\"val_mae\"]}  > umbral 32.0'
          "

  deploy:
    needs: train-and-evaluate
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - name: Register model in MLflow
        run: python src/register_model.py
      - name: Deploy to staging API
        run: kubectl apply -f k8s/staging/
      - name: Run smoke tests
        run: python src/smoke_tests.py --env staging
      - name: Promote to production
        run: kubectl apply -f k8s/production/
```

## 6. Patrones de despliegue

### 6.1 Serving en tiempo real — API REST

El patrón más común es envolver el modelo en una API REST:

```python
# FastAPI + MLflow
from fastapi import FastAPI
import mlflow.pyfunc
import pandas as pd

app = FastAPI(title="API de predicción de demanda")
model = mlflow.pyfunc.load_model("models:/demanda_supermercado/Production")

@app.post("/predict")
async def predict(features: dict):
    df = pd.DataFrame([features])
    prediction = model.predict(df)
    return {"demanda_predicha": float(prediction[0]),
            "modelo_version": "v3.2",
            "timestamp": pd.Timestamp.now().isoformat()}

@app.get("/health")
async def health(): return {"status": "ok"}
```

**Contenedores Docker** garantizan que el entorno de producción es idéntico al de desarrollo:

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY src/ ./src/
COPY models/ ./models/
EXPOSE 8000
CMD ["uvicorn", "src.api:app", "--host", "0.0.0.0", "--port", "8000"]
```

### 6.2 Batch prediction

Para casos donde la latencia no es crítica, la inferencia batch es más eficiente:

```python
# Proceso batch nocturno: predecir demanda del día siguiente para todos los SKUs
from airflow import DAG
from airflow.operators.python import PythonOperator

def predict_batch(**context):
    model = load_model()
    features = load_features_from_store(date=context["ds"])
    predictions = model.predict(features)
    save_predictions(predictions, date=context["ds"])

with DAG("batch_demand_prediction", schedule_interval="0 22 * * *") as dag:
    t1 = PythonOperator(task_id="load_features", python_callable=load_features)
    t2 = PythonOperator(task_id="predict",       python_callable=predict_batch)
    t3 = PythonOperator(task_id="save_results",  python_callable=save_predictions)
    t1 >> t2 >> t3
```

### 6.3 Patrones de despliegue gradual

**Blue-Green deployment:** dos entornos idénticos (blue = producción actual, green = nueva versión). El tráfico se redirige completamente a green cuando pasa las pruebas. Rollback instantáneo.

**Canary deployment:** el nuevo modelo recibe un porcentaje pequeño del tráfico (e.g., 5%) mientras el antiguo sirve el resto. Si las métricas son satisfactorias, se incrementa gradualmente a 100%.

**Shadow mode:** el nuevo modelo predice en paralelo pero sus predicciones no se sirven al usuario — solo se registran para comparación. Permite evaluar en producción real sin riesgo.

**A/B testing:** dos variantes del modelo se sirven a subgrupos distintos de usuarios. La diferencia en métricas de negocio (conversión, retención) determina el ganador.

> [!example] Ejemplo 2 — Despliegue de un modelo de recomendación en plataforma de streaming
> **Shadow mode (2 semanas):** el nuevo modelo de recomendación (Transformer-based) predice en paralelo con el modelo de producción (Matrix Factorization). Las predicciones del nuevo modelo se registran pero no se muestran al usuario. Se verifican: latencia de inferencia (<80ms P99), sin crashes, distribución de predicciones razonable.
> **Canary (1 semana):** 5% del tráfico al nuevo modelo. Métricas de negocio monitoreadas: CTR (click-through rate), tiempo de visionado, tasa de abandono. Si CTR mejora +2% sin degradar otras métricas → continuar.
> **Despliegue completo:** tráfico migrado al 100% en 3 días. El modelo antiguo permanece disponible 30 días para rollback de emergencia.

## 7. Monitoreo de modelos en producción

### 7.1 Los tres tipos de drift

<font color="#00b0f0">Definición 4 — Data drift, concept drift y prediction drift</font>

**Data drift** (covariable shift): la distribución de las características de entrada $P(X)$ cambia entre entrenamiento y producción. El modelo puede no haber visto regiones del espacio de características que ahora son frecuentes.

**Concept drift**: la relación entre características y etiqueta $P(Y|X)$ cambia. El modelo sigue viendo las mismas entradas pero el mundo ha cambiado (e.g., el comportamiento de compra cambió tras una crisis económica).

**Prediction drift**: la distribución de las predicciones $P(\hat{Y})$ cambia, incluso si $P(X)$ no lo hace. Puede indicar un bug en el pipeline de serving.

### 7.2 Detección de drift

**Test de Kolmogorov-Smirnov (KS):** para variables continuas, compara la distribución de entrenamiento $F_{\text{train}}$ con la de producción $F_{\text{prod}}$:

$$D_{KS} = \sup_x |F_{\text{train}}(x) - F_{\text{prod}}(x)|, \quad p\text{-valor} = P(D_{KS} \geq d_{\text{obs}} \mid H_0)$$

Si $p < 0.05$ → drift estadísticamente significativo.

**Population Stability Index (PSI):** mide el cambio en la distribución de una variable o de las predicciones:

$$\text{PSI} = \sum_{b=1}^B (p_b^{\text{prod}} - p_b^{\text{train}}) \cdot \ln\!\frac{p_b^{\text{prod}}}{p_b^{\text{train}}}$$

Interpretación estándar: PSI < 0.1 → sin cambio notable; 0.1–0.25 → cambio moderado; > 0.25 → cambio severo, re-entrenamiento necesario.

**Classifier-based drift detection:** entrenar un clasificador para distinguir datos de entrenamiento vs. producción. Si el AUC del clasificador es > 0.7, las distribuciones son distinguibles → drift detectado.

### 7.3 Monitoreo de métricas de negocio

Las métricas técnicas del modelo (RMSE, AUC) solo son observables con etiquetas verdaderas, que a menudo llegan con retraso (días, semanas). Las **métricas de proxy** son observables en tiempo real:

- **Distribución de predicciones:** si el modelo siempre predice valores extremos → posible drift
- **Tasas de rechazo / confianza:** fracción de predicciones con baja probabilidad de confianza
- **Métricas de negocio:** conversión, clics, ventas — el indicador definitivo de salud del modelo

### 7.4 Estrategias de re-entrenamiento

| Estrategia | Cuándo usar | Pros | Contras |
|---|---|---|---|
| **Programado** (diario/semanal) | Datos que cambian regularmente | Simple, predecible | Innecesario si no hay drift |
| **Basado en drift** | Cuando se detecta cambio significativo | Eficiente | Requiere umbral bien calibrado |
| **Basado en rendimiento** | Cuando métricas de negocio caen | Alineado al objetivo | Etiquetas con retraso |
| **Online learning** | Datos en streaming, modelos adaptativos | Sin batch re-training | Difícil de estabilizar |

> [!example] Ejemplo 3 — Monitoreo de modelo de detección de fraude bancario
> Un modelo XGBoost detecta transacciones fraudulentas. Las etiquetas verdaderas (¿fue fraude?) llegan con retraso de 30–60 días (cuando el banco confirma la reclamación). El monitoreo usa métricas de proxy: distribución de scores de fraude (PSI diario), tasa de alertas generadas, distribución del monto de transacciones (KS semanal). Cuando PSI > 0.15 en el score → alerta. El re-entrenamiento automático (Airflow) se dispara si PSI > 0.25 o si la precision en las últimas 1.000 transacciones etiquetadas cae > 5 puntos porcentuales. El nuevo modelo pasa por shadow mode 48h antes de reemplazar al anterior.

## 8. Equidad y sesgos en sistemas ML

### 8.1 Fuentes de sesgo

- **Sesgo histórico:** los datos de entrenamiento reflejan desigualdades históricas (e.g., modelos de crédito entrenados en datos donde grupos minoritarios tenían menos acceso)
- **Sesgo de muestra:** la muestra de entrenamiento no es representativa de la población de despliegue
- **Sesgo de medición:** la variable objetivo o las características se miden con distinta precisión para distintos grupos
- **Sesgo de retroalimentación:** el modelo influye en los datos futuros (e.g., un modelo de predicción de reincidencia afecta las decisiones judiciales, que afectan los datos futuros)

### 8.2 Métricas de equidad

<font color="#00b0f0">Definición 5 — Paridad demográfica, equidad de oportunidad e igualdad de tasa de error</font>

Sea $A$ el atributo protegido (género, raza, edad), $\hat{Y}$ la predicción y $Y$ la etiqueta verdadera.

**Paridad demográfica:** $P(\hat{Y}=1|A=0) = P(\hat{Y}=1|A=1)$ — misma tasa de predicciones positivas para todos los grupos.

**Equidad de oportunidad (Hardt et al., 2016):** $P(\hat{Y}=1|Y=1,A=0) = P(\hat{Y}=1|Y=1,A=1)$ — misma tasa de verdaderos positivos (recall) para todos los grupos.

**Igualdad de tasas de error:** TPR y FPR iguales para todos los grupos. Nota: es matemáticamente imposible satisfacer simultáneamente paridad demográfica, equidad de oportunidad e igualdad de tasas de error cuando las tasas base difieren entre grupos (Chouldechova, 2017).

> [!warning] La imposibilidad de la equidad perfecta
> Chouldechova (2017) y Kleinberg et al. (2017) demostraron que las definiciones de equidad son mutuamente incompatibles cuando las tasas base de la variable objetivo difieren entre grupos. No existe un modelo perfectamente justo según todas las definiciones simultáneamente. La elección de qué métrica de equidad optimizar es una **decisión de valores**, no técnica.

## 11. Propiedades y advertencias clave

> [!tip] El training-serving skew — el bug más silencioso
> El **training-serving skew** ocurre cuando el preprocesamiento en producción difiere del aplicado durante el entrenamiento. Causas comunes: aplicar el scaler con parámetros distintos, imputar faltantes con la mediana del dataset de producción en vez de la del entrenamiento, usar una versión distinta del feature engineering. Solución: serializar el pipeline completo (incluyendo preprocesamiento) con un solo objeto y cargarlo en producción. Nunca reproducir el preprocesamiento manualmente en el serving.

> [!tip] Feature stores para consistencia online/offline
> Las características calculadas offline (lags de 28 días, medias rodantes mensuales) deben ser exactamente las mismas en entrenamiento y en serving. Un feature store centralizado garantiza esto: el proceso de entrenamiento y la API de serving leen de la misma fuente. Sin feature store, el código de cálculo de características se duplica y diverge.

> [!warning] Nunca usar datos de test para decisiones de pipeline
> El conjunto de test debe estar completamente separado desde el inicio del proyecto — antes de cualquier decisión sobre preprocesamiento, selección de variables o arquitectura del modelo. Usar datos de test para ajustar el pipeline es data leakage estructural que invalida la estimación del error de generalización.

> [!warning] El costo oculto del re-entrenamiento continuo
> Re-entrenar frecuentemente tiene costos: tiempo de cómputo, consumo energético, tiempo de evaluación y validación, riesgo de introducir regresiones. El re-entrenamiento innecesario es un desperdicio. Calibrar correctamente los umbrales de drift (PSI, KS) y las métricas de negocio es fundamental para que el trigger de re-entrenamiento sea justo — ni demasiado sensible ni demasiado insensible.

> [!note] MLOps maturity levels
> Google y Microsoft definen niveles de madurez de MLOps:
> - **Nivel 0:** entrenamiento manual, despliegue manual, sin monitoreo. El notebook es el artefacto principal.
> - **Nivel 1:** pipelines automatizados de entrenamiento, monitoreo básico, despliegue semi-manual.
> - **Nivel 2:** CI/CD completo, re-entrenamiento automático basado en drift, feature store, tests automatizados de datos y modelo.
>
> La mayoría de equipos opera en Nivel 0 o 1. El Nivel 2 requiere inversión significativa en infraestructura pero reduce el tiempo de iteración de semanas a horas.

class CyclicalTransformer(BaseEstimator, TransformerMixin):
    """Codifica variables cíclicas con sin/cos."""
    def __init__(self, columns_max):
        self.columns_max = columns_max  # dict: {col_name: max_value}
    def fit(self, X, y=None):
        return self
    def transform(self, X):
        X = pd.DataFrame(X).copy()
        result = {}
        for col, max_val in self.columns_max.items():
            col_idx = list(self.columns_max.keys()).index(col)
            vals = X.iloc[:, col_idx].values if hasattr(X,'iloc') else X[:, col_idx]
            result[f"{col}_sin"] = np.sin(2 * np.pi * vals / max_val)
            result[f"{col}_cos"] = np.cos(2 * np.pi * vals / max_val)
        return np.column_stack(list(result.values()))

# ─── Sección 5: detección de drift (PSI) ───────────────────────
def compute_psi(expected, actual, n_bins=10):
    """Population Stability Index entre dos distribuciones."""
    bins = np.percentile(expected, np.linspace(0, 100, n_bins+1))
    bins[0] -= 1e-6; bins[-1] += 1e-6
    p_exp = np.histogram(expected, bins=bins)[0] / len(expected)
    p_act = np.histogram(actual,   bins=bins)[0] / len(actual)
    p_exp = np.where(p_exp==0, 1e-6, p_exp)
    p_act = np.where(p_act==0, 1e-6, p_act)
    return np.sum((p_act - p_exp) * np.log(p_act / p_exp))

    X_prod = X_test.copy()
    X_prod["temp_exterior"] = X_prod["temp_exterior"] + drift_magnitude
    prod_preds = pipeline.predict(X_prod)
    psi_score  = compute_psi(train_preds, prod_preds)
    status = "🟢 OK" if psi_score < 0.10 else "🟡 Moderado" if psi_score < 0.25 else "🔴 ALERTA"
    print(f"Drift temp +{drift_magnitude:2d}°C → PSI={psi_score:.4f} {status}")

         - velocidad_v * 0.8

    # Codificación cíclica de hora y dia_semana

        dia_cos  = cos(2*pi*dia_semana/7)

    step_rm(hora, dia_semana) |>

# ─── Sección 6: monitoreo de drift PSI ───────────────────────────
compute_psi <- function(expected, actual, n_bins=10){
    breaks <- quantile(expected, probs=seq(0,1,length.out=n_bins+1))
    breaks[1] <- breaks[1]-1e-6; breaks[n_bins+1] <- breaks[n_bins+1]+1e-6
    p_exp <- hist(expected, breaks=breaks, plot=FALSE)$counts / length(expected)
    p_act <- hist(actual,   breaks=breaks, plot=FALSE)$counts / length(actual)
    p_exp[p_exp==0] <- 1e-6; p_act[p_act==0] <- 1e-6
    sum((p_act - p_exp) * log(p_act/p_exp))
